## 2. Rationale for Each Change
- **Zero-Heap `.bss` `StaticMp3Decoder`**:
  The previous MP3 implementation failed on hardware with FreeRTOS heap exhaustion / OOM because it heap-allocated a ~23 KB `Decoder` box and a ~9.2 KB sample buffer. `StaticMp3Decoder` is a `no_std`, `const fn`-initializable struct residing in `.bss`. It decodes directly into the pipeline's `pcm_out` buffer, requiring zero heap allocations during runtime.
- **Sync Alignment & Partial-Frame Guard**:
  When reading MP3 streams (especially after HTTP header parsing or ICY chunks), the stream buffer may end in a partial MP3 frame or contain non-sync bytes. The guard scans for sync words (`0xFF 0xFB/0xF3/0xF2`) and enforces `encoded_in.len() < frame_bytes + 4 -> NeedMoreData`, preventing truncated frames from corrupting the decoder's bit reservoir.
- **ICY Metadata Stripping & `cont` `metaint` Handling**:
  Internet radio streams interleave metadata blocks every `metaint` bytes. The HTTP reader tracks bytes consumed and strips metadata blocks inline without advancing playback or stream bytes counters.
- **Exact HTTP Header Parsing**:
  `audio_sock.recv(|rx_buf| ...)` inspects the socket receive buffer and consumes only up to the exact end of `\r\n\r\n`, leaving body byte 0 in the TCP socket. This prevents the initial MP3 frame header from being lost.
- **Xtensa Compiler Patch for `nanomp3-core`**:
  Xtensa's LLVM backend crashed with `Cannot select: i32 = Constant<4608>` when compiling `l3_decode` because `Scratch` placed 4608-byte `grbuf` ahead of other fields, generating GEP offsets of 4608 that the instruction selector could not legalize. Separating arguments into individual pointers solved this at the ABI level cleanly.

## 3. Known Risks & Untested Assumptions
1. **Live ICY Metadata Payload Variability**:
   Different radio servers may omit `icy-metaint` or send non-zero length metadata without title strings. The code defaults to standard transparent streaming if `icy_meta_interval == 0`.
2. **Flash OTA Partition Sizing**:
   The resulting binary is 749,808 bytes, which uses 27.91% of the 2,686,976 byte `ota_0` partition on `BASEMENT`. There is abundant margin (over 1.9 MB free).
3. **Hardware Playback Verification**:
   This subagent strictly executed `--stage-only` verification. Target hardware (`172.22.1.15` and `/dev/ttyUSB0`) was not touched and must be verified in a subsequent OTA flash work order.
