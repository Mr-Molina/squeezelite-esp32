## 2. Rationale for Each Change
- **Root Cause Resolution**:
  During boot in `WO-050`, the ESP32 panicked with a stack overflow because the initial call frame of `run_hardware_firmware()` + `load_nvs_wifi_credentials()` consumed 28,984 bytes of stack, exceeding the linker-allocated `.stack` size of 27,824 bytes.
- **`.bss` Memory Overlay for `nvs_buf`**:
  `nvs_buf` is only needed during initial boot before Wi-Fi is active and before audio streaming begins. By passing `fw_bufs.ring_storage` (16,384 bytes) to `load_nvs_wifi_credentials()`, the 16 KB stack allocation was completely eliminated with 0 extra bytes of BSS.
- **Static Decoder BSS Placement**:
  By initializing `sample_rate: 0` in `StaticMp3Decoder::new()`, `STATIC_MP3_DEC` became entirely zero-initialized, moving from `.data` to `.bss`. This shrank the raw `.data` section by 22,804 bytes and reduced the flashed binary image by 22,496 bytes.
- **Right-Sizing Protocol Buffers**:
  Buffers in `FirmwareBssBuffers` were right-sized according to actual max packet requirements. This freed 10,752 bytes from `.bss`, which directly expanded the available `.stack` partition in `dram_seg`.
- **Linker Section Verification**:
  `xtensa-esp32-elf-readelf -S` proved that `.stack` expanded to 38,576 bytes (`> 37 KB`, `>= 38,000 B`), providing +9,592 bytes of headroom above the peak boot stack demand.

## 3. Known Risks & Untested Assumptions
1. **Network Buffer Sizing Under Extreme Network Jitter**:
   `audio_rx_buf` was right-sized from 8192 to 4096 bytes and `slim_tx_buf` from 4096 to 1024 bytes. These sizes are well above standard MTU and SlimProto frame sizes (max SlimProto frame is 2048 bytes for HELO/STAT, audio chunks are typically 1024-2048 bytes).
2. **Flash Staging**:
   This subagent operated under strictly `--stage-only` execution. Device `172.22.1.15` and `/dev/ttyUSB0` were not accessed.
